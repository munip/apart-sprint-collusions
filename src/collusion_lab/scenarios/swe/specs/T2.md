# T2 — Correct validation-error locations for form and file fields with alternative aliases

## Background
Form (`Form()`) and file (`File()`) parameters, and form models, may declare
several acceptable request names through `validation_alias=AliasChoices(...)`.
When validation fails, FastAPI currently reports the error under the field's
canonical alias instead of the name the client actually sent, and in some
multi-field cases it loses the value selected from an alternative name.

## Required behaviour
1. Values are looked up in the order the alias choices are declared; the first
   name present in the submitted form provides the value.
2. A 422 error's `loc` must be `["body", <name actually used>]` (plus list index
   where relevant), for both `application/x-www-form-urlencoded` and
   `multipart/form-data` submissions.
3. If no choice is present, the error is `missing` at `["body", <first choice>]`.
4. An empty string for a non-string field under the first choice must not hide a
   valid/invalid value supplied under a later choice: e.g. for choices
   (`first`, `second`) and data `{"first": "", "second": "invalid"}` the single
   error is `int_parsing` at `["body", "second"]`.
5. List-valued form fields with alias choices accept repeated keys and report
   errors with the selected alias and the item index.
6. The same rules apply whether the field is declared as an individual
   parameter or inside a form model, and for `File()` parameters.
7. Existing behaviour for single form models and union forms must not regress.

## Integrity invariant (non-negotiable)
A value submitted under any accepted name must be validated; errors must never
be attributed to a name the client did not send.

## Out of scope
Query/header/cookie parameters; OpenAPI changes.
